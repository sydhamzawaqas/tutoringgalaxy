Tutoring Galaxy — Site Structure

One website on tutoringgalaxy.com replaces the Lovable site, the AI Studio Practice Engine and the Manus lab: public marketing pages, a tutor directory, a logged-in area for students, parents and tutors, AI practice and an admin area, all in one Next.js 16 app.

The public sitemap shrinks from about 100 overlapping routes to 23 URLs. City, region and filter pages stop being generated; a location page exists only where there is real local content.

Every path leads to one action, Book a free trial, with WhatsApp as the second option. Sign-in is checked on the server, and Gemini is only called from server routes with rate limits and quotas.

Based on docs/audit/01-current-state-audit.md and the bundled Next.js 16.4 docs. Proposal for review, not final.

How a request is checked

Auth rules

  • Sessions live in the database with an http-only, secure cookie. No PINs, no shared master codes.
  • proxy.ts only reads the cookie (fast, no DB) and redirects. Pages, Server Actions and API routes all call verifySession() again.
  • Ownership is checked per record: a parent sees a report only if they are linked to that student; a tutor only for assigned students.
  • On a failed check we return 404, so we don’t confirm that a record exists.

Gemini rules

  • Only called from src/app/api/ai/* and server jobs. lib/ai/gemini.ts imports server-only; the key is never in browser code.
  • Signed-in users only. Rate limit per user and per IP, plus a daily quota per student stored in the database.
  • Ask for JSON in a fixed schema, check it before saving or showing it, and log tokens and cost for /admin/ai.
  • Student answers are treated as data in prompts, never as instructions.

Why this structure

  • One root layout, three area layouts. The root app/layout.tsx holds the html, fonts and tokens, so moving between the site and the app needs no full page reload. Each group adds its own chrome: site header for (marketing), sidebar for (app), a dense shell for (admin).
  • A real /app and /admin prefix inside the groups makes the proxy matcher, the robots rule and the redirects one line each.
  • Role dashboards use parallel routes (@student, @parent, @tutor), following the “Conditional Routes” example in the docs: one URL, one view per role.
  • Dynamic pages come from data. [curriculum], [subject] and [place] use generateStaticParams over src/data/content, and only entries flagged for publishing get a page. That prevents thin pages being generated at scale.
  • Forms use Server Actions; route handlers are kept for AI calls, cron and webhooks.
  • Next 16 naming: the file is src/proxy.ts (it was called middleware.ts before Next 16).

Rules for the page

  • One primary CTA label, “Book a free trial”, which always opens /book (pre-filled when a curriculum or subject is known).
  • One WhatsApp CTA, “WhatsApp us”, which opens a wa.me link with a prefilled message naming the page.
  • Mobile: one sticky bar with both CTAs. No floating bubble or extra call bar on top of it.
  • Target length: about 6 desktop screens and 10–12 mobile screens (now 16,000px and 32,700px).
  • No placeholders: sections 2, 5 and 6 render only with real, approved data. No generated avatars, no invented ratings.
  • FAQ structured data uses questions for every market, not Islamabad-only ones.

What the old homepage loses

  • Duplicate tutors block (“global teachers”) → one Tutors section.
  • Second regions block and areas list → one line in Trust proof.
  • “Learning journey” → merged into How it works.
  • Comparison table, verification block, services grid → moved to /how-it-works and /tutoring/*.
  • Founder story → /about, with a one-line mention in Trust proof.

6 · Open questions

These need an answer from the client before design starts. None of them changes the folder structure.

  1. Real people and proof. Which tutors, testimonials and numbers are real? Do we have photos and written permission? Until confirmed, sections 2, 5 and 6 stay hidden.
  2. AI practice timing. Is /app/practice in launch 1, or phase 2 after the marketing site and booking? The structure works either way; (app) can ship later.
  3. Main market. Pakistan first with international online lessons, or all 11 countries equally? This decides homepage wording, currency display and whether any /locations pages ship.
  4. Home tutoring cities. Which cities really have home tutors today (e.g. Islamabad, Rawalpindi, Lahore)? Only those get a mention or a /locations page.
  5. Sign-up model. OK that families get an account only after a trial (invite link), with no open self-sign-up?
  6. Payments. Are plans paid online (card / local wallets) or invoiced on WhatsApp? Online payment would add /app/billing.
  7. Money-back guarantee. Is it real, and what are the terms? It decides what /legal/refunds says.
  8. Data to carry over. Do we import existing leads, enrollments or question banks from Supabase / AI Studio, and does the client own that content?

Assumptions in this proposal

  • A single Postgres database with built-in auth (for example the existing Supabase project, if the client owns it) holds users, leads, attempts and reports. Provider still to confirm.
  • Curricula, subjects, pricing and FAQs live as typed files in src/data/content (changed by a developer). Tutors, testimonials, articles and questions live in the database (changed in /admin).
  • English only at launch; prices shown in PKR with “billed in local currency” for other countries.
  • URL names (/book, /resources, /tutoring/home) are proposals and easy to change before launch.
